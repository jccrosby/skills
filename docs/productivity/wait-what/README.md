# Wait-what

## Purpose

This skill re-pitches a previous answer, recommendation, or proposal in clear, direct language from the perspective of the current project. It applies ASD-STE100 Simplified Technical English rules to make the message simple, actionable, and grounded in project context.

## When to use it

Choose it when:

- a previous answer or proposal is technically sound but needs a clearer pitch,
- the wording is too long, too abstract, or too generic for the current situation,
- you need to explain an idea to a decision maker or project team in plain language,
- or the message lacks a clear link to the project's goals and constraints.

## Workflow

1. Read and understand the previous response or proposal.
2. Identify the core message: what is proposed, why it matters, and what action is needed.
3. Review the current project context, constraints, and goals.
4. Reframe the idea from the project's perspective, not in abstract or general terms.
5. Rewrite the content following ASD-STE100 rules: short sentences, one idea per sentence, plain words, active voice, no idioms.
6. Make the output practical: state what the project gains, what is required, what risk exists, and what the next step is.
7. End with a clear recommendation or decision point.

## Output pattern

Frame the re-pitched response as follows:

- **Current project context:** What the project is doing right now.
- **What we are doing:** The specific proposal or recommendation.
- **Why this matters now:** Why this is relevant to the project at this moment.
- **What the project gains:** Concrete benefits or outcomes.
- **What we need to do:** Required actions or resources.
- **Risk or constraint:** Any trade-offs, blockers, or limitations.
- **Recommended next step:** Clear action for a decision maker.

Then provide a polished summary in plain ASD-STE100 language.

## ASD-STE100 principles

- Use short sentences.
- Use one idea per sentence.
- Use plain words.
- Do not use sarcasm, jokes, or idioms.
- Do not use marketing language.
- Define terms if they may be unclear.
- Use direct language over abstract language.
- Keep focus on the project, the user, and the result.

## Good practice

- Ground every statement in the project context.
- Be specific about what the project gains.
- State what is required and what is at risk.
- Keep the message shorter and clearer than the original.
- End with a practical next step.
- Do not invent facts; use what you know from the prior answer and the project.

## Common pitfalls

- Re-pitching in the same abstract language as the original.
- Losing connection to the current project goals or constraints.
- Including unnecessary detail or background that does not add value.
- Ending without a clear recommendation or action.
- Inventing facts to fill gaps; instead, state the gap clearly.
- Over-simplifying and losing important technical accuracy.
